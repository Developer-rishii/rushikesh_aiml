# Task 15 — Intelligence Layer Integration & Model Governance

**PlaceMux · Phase 3 · Sprint C · AI/ML Engineer**

> "The bar: Any model in production can be traced, explained, rolled back and
> is watched for decay." — Task 15 study guide, Section 1

This repo is a working implementation, not a design doc: it generates
realistic logged data, trains a real ranker, registers it with lineage,
detects a real injected drift event, retrains and re-gates a new version,
demonstrates a live rollback, injects a real failure, and writes every
number to disk as evidence. Nothing described below is asserted without a
corresponding file you can open.

## Run it yourself

```bash
pip install -r requirements.txt
python3 -m pytest tests/ -v          # unit evidence
python3 -m demo.run_end_to_end       # full Stage E integration run
```

Everything is deterministic (seeded RNG) — rerunning reproduces the same
numbers reported here.

## What "good" means here (Stage A, done explicitly before building)

- **Bar for the registry:** every promoted model must be traceable back to
  its exact training data (content hash) and feature contract (schema
  hash), and any prior version must be restorable as production in O(1).
- **Bar for drift detection:** must catch both covariate drift (input
  distributions shift) and concept drift (input→label relationship shifts)
  independently, because either can happen without the other.
- **Bar for the model card:** must be regenerated per version from actual
  measured numbers, never hand-written, so it cannot go stale or become "a
  formality" (an explicit Pitfall, Section 12).
- **Baseline to beat:** `SkillMatchBaseline` — ranking by
  `skill_match_score` alone, i.e. what a naive keyword-matcher does. A
  ranker that can't beat this on held-out nDCG@10 does not ship.

## Design decisions made and alternatives rejected (Section 8)

1. **Registry backing store:** SQLite file registry, not an MLflow server
   process. Rejected MLflow because this environment has no persistent
   server and MLflow's own local backend is SQLite anyway — same
   guarantees, zero extra infra, and the schema maps 1:1 for a future
   migration.
2. **Retraining trigger: drift-triggered, not purely scheduled.** A
   scheduled-only cadence (e.g. weekly) would leave a silently-wrong model
   serving for days after a sudden shift like an embedding-model swap.
   Drift-triggered retraining catches that same day. A scheduled minimum
   cadence is still recommended as a belt-and-suspenders safety net in
   case the drift signal itself fails silently.
3. **Promotion: human-in-the-loop gate, not full automation.** Because
   this model affects hiring outcomes (fairness + DPDP constraints,
   Section 3), a candidate model is only promoted if it clears BOTH the
   offline-beats-baseline gate AND the fairness gate — logged in the audit
   trail as `approved_by`. Full auto-promotion was rejected because it
   could silently ship a fairness regression.
4. **Ranking objective: LambdaMART (listwise), not pointwise
   classification.** Section 5 explicitly warns "ranking is not
   classification" — pointwise objectives optimize calibration, not order,
   and PlaceMux serves a ranked list per job. The pointwise baseline is
   kept only as the bar to beat, never as a production candidate.
5. **Fairness threshold: top-k selection rate, not an absolute score
   cutoff.** LambdaMART produces unbounded relevance scores, not
   calibrated probabilities — a fixed `>=0.5` cutoff silently produced
   zero "positives" in both groups on first attempt, which would have made
   the fairness gate pass vacuously. Fixed to use "ranked in the top 20%"
   as the positive prediction, matching what a recruiter actually sees.

## Brainstorming answers (Section 9)

- **"How would you know the model rotted before users tell you?"** —
  `DriftDetector` runs PSI on every serving feature plus a performance
  check against the metric the production model shipped with, independent
  of any user complaint; see `governance/drift_reports/`.
- **"Can you reproduce the exact model that made a decision last
  quarter?"** — Yes: `registry.get(version)` returns the artifact path,
  training-data content hash, and feature-schema hash for any version ever
  registered, and `promotions` records exactly which version was live at
  any timestamp.
- **"Who signs off a model that affects hiring?"** — The promotion gate
  requires both automated checks (baseline + fairness) and, for
  drift-triggered retrains, an `oncall_review` approver recorded in the
  audit trail — never a silent auto-ship.

## Pitfalls checklist (Section 12) — addressed, not just avoided in theory

- [x] Rollback path exists and was exercised live, not just coded.
- [x] Retraining has an evaluation gate (v2 only promoted after beating v1
      on held-out post-drift data + passing fairness).
- [x] Offline win is checked against an online proxy metric before being
      trusted (`online_proxy_validation` in evidence).
- [x] Fairness audit runs on every version's registration, not once at the
      end (`model_card.py` regenerates it per version).
- [x] Every model is versioned with a content hash of its training data —
      "which model made this decision six months ago" is answerable.

## Known limitations (stated up front, not discovered later)

- Data is simulated, not pulled from a live PlaceMux database — but the
  schema and pipeline are written so swapping `generate_data.py`'s output
  for a real export changes nothing downstream (see docstring in that
  file).
- Binary relevance label only (`shortlisted`); graded relevance
  (click/apply/shortlist) is noted as future work in every model card.
- Fairness audit covers the `gender` attribute recorded in the dataset
  only; `region` is logged but not separately gated in this version.
