# Task 21 — Cost Optimization & FinOps (AI/ML Engineer, Sprint E)

This repo is a complete, **run** solution to Task 21 from the PlaceMux
Phase 3 study guide: *"Cut the cost of intelligence: cost per inference,
per training run and per shortlist... materially cheaper intelligence at
the same quality, with the unit economics documented."*

Everything below was generated by actually executing the code in this
repo (`reports/evidence.json`, `reports/cost_before_after.csv`,
`experiments/experiment_log.md`) — no numbers here are hand-typed claims.

## 1. Where this fits / the bar (Stage A)

- **Bar to clear:** show cost per inference, per training run, and per
  shortlist, before and after optimization, at **held-constant quality**,
  plus one live failure drill — with evidence, not slides.
- **Data:** This pipeline runs on the **MovieLens 100K** dataset — a real,
  public, freely-licensed interaction/rating log (100,000 ratings from
  943 users on 1,682 items). Ratings are mapped to a click/shortlist/
  application funnel, user demographics provide a protected-group flag
  for fairness slicing, and item genre features serve as ranking signals.
  See [Dataset](#dataset-movielens-100k) section below for license and citation.

## 4. Deliverables (Section 2 learning objectives)

### 4a. Cost model for the intelligence layer (train + serve)
`src/cost_model.py` — unit prices (INR) for CPU/GPU instance-hours and
throughput live in one config table (`UNIT_PRICES_INR`), not buried in
logic, so it maps directly onto a real cloud billing export. Produces:
train cost (₹), serve cost per 1000 inferences (₹), and cost per
shortlist (₹) — the metric that ties spend to business value, not just
compute.

### 4b. Optimizations reducing cost per inference/shortlist
`src/optimizations.py`, three applied together:
1. **Right-sizing** — GPU → CPU serving (most inference doesn't need a GPU).
2. **Caching** — dedupe repeat `(job_id, candidate_id)` scoring requests.
3. **Precompute vs on-demand** — nightly batch-score the head jobs
   (top 20% by traffic), keep on-demand only for the long tail.
Plus a smaller model (`n_estimators=60, max_depth=3` vs baseline's
`400, 6`) trained on identical data/features.

### 4c. Before/after cost, quality held constant
From `reports/evidence.json` (actual run output):

| | Baseline (big model, GPU) | Optimized (small model, CPU, cached, precomputed) |
|---|---|---|
| nDCG@10 | 0.5794 | 0.5722 (Δ −0.0072, within ±0.01 tolerance → **quality held constant**) |
| Serve cost / 1000 inferences | ₹0.0156 | ₹0.0033 (**−78.85%**) |
| Cost / 10,000 shortlists | ₹0.56 | ₹0.12 (**−78.57%**) |
| Train cost (per run) | ₹76.44 | ₹0.30 |

## 5. Model Versioning & Governance

Every pipeline run registers each model (baseline and optimized) to
`models/registry.json` with:
- **Version ID** (e.g. `baseline_v1`, `optimized_v2`)
- **Config hash** (MD5 of hyperparameters + data length)
- **Timestamp**
- **Eval metrics** (nDCG@10, precision@k)
- **Cost metrics** (serve cost per 1000 inferences)
- **Data snapshot size**

Re-running the pipeline **appends** new versioned entries rather than
overwriting, so you can always trace which model produced a decision at
any point in time.

A **Model Card** (`reports/model_card_<version>.md`) is auto-generated
per version with data snapshot used, nDCG@10, cost/1000, and date — per
the guide's "Go deeper" section on model cards.

`reports/evidence.json` records which model versions (`baseline_version`,
`optimized_version`) produced the evidence in that run.

## 6. Verification (Stage E, live-demoable)

- **Offline vs online gap** (Section 5, "online is the truth"): reported
  side by side — offline nDCG@10 vs online CTR proxy from real click
  logs — in `evidence.json["offline_online_gap"]`, not offline alone.
- **Train/serve skew check** (Section 5's "single biggest silent
  killer"): simulates a stale-cache feature path at serve time and
  measures prediction drift (`evidence.json["train_serve_skew"]`).
- **Fairness slice** (Pitfall: "audit done once, at the end, as a
  formality" — done here as a standing check, not a one-off): top-quartile
  selection rate compared across the two protected-group cohorts.
- **Failure injection drill** (Stage E.3): scoring service forced down
  (`fail_rate=1.0`) for 500 live requests. Result: 0 requests errored;
  all served via cache or a cheap heuristic fallback
  (`evidence.json["failure_injection"]`). This is also the answer to
  "what happens when the model is unavailable" required in every stage.
- **Reproducibility**: every run appends inputs, model config, and
  results to `experiments/experiment_log.md`.

## 7. Alternative approaches considered (Section 8)

- **Precomputing nightly vs real-time inference** — chose a **hybrid**:
  precompute only the head (top 20% of jobs = ~65% of traffic) and stay
  on-demand for the tail. Pure nightly precompute was rejected because
  the long tail (single-digit views/job) would waste >75% of precompute
  spend on jobs nobody looks at before the next refresh; pure on-demand
  was rejected because it throws away the highest-value caching
  opportunity (head jobs are viewed by many candidates).
- **Smaller model vs aggressive caching** — did **both**, deliberately,
  because they attack different cost sources: right-sizing cuts the
  per-inference compute cost, caching cuts the inference *count*. Using
  only one leaves the other lever on the table.

## 9. Pitfalls checklist (Section 12) — how each is addressed here

| Pitfall | Addressed by |
|---|---|
| Cost unknown per unit | `cost_model.py` gives ₹/inference, ₹/train-run, ₹/shortlist explicitly |
| Cost cut by silently degrading quality | nDCG delta computed and gated (`quality_held_constant` flag) before claiming a win |
| Offline win never validated online | `offline_online_gap` reports both, side by side |
| Fairness audit as one-off formality | slice metric computed every run, not appended manually at the end |
| No model versioning | Every model versioned in `models/registry.json` with hash/timestamp/config; model cards auto-generated; evidence.json records which version produced each result |

- **Name:** MovieLens 100K
- **Source:** [GroupLens Research](https://grouplens.org/datasets/movielens/100k/)
- **License:** Free for research use. See [README](https://files.grouplens.org/datasets/movielens/ml-100k-README.txt) from GroupLens.

  Systems* 5, 4, Article 19 (December 2015), 19 pages.

- **Mapping to pipeline schema:** User ratings (1–5) are mapped to a
  click (≥3) / shortlist (≥4) / application (=5) funnel. User age

  Romance) serve as ranking features. User gender provides a
  protected-group cohort for fairness slicing.
