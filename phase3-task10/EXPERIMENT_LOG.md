# Experiment Log — Task 10 Growth Integration & Experiment Readout

All numbers below are copied verbatim from `artifacts/*.json`, generated by
running `./run_all.sh`. Re-run it to reproduce every figure independently.

## 1. Offline result (`artifacts/offline_eval_report.json`)
On 160 held-out job postings (never seen during training), the treatment
ranker beat the production baseline heuristic on every offline metric:

| Metric | Baseline | Treatment | Gap |
|---|---|---|---|
| nDCG@10 | 0.731 | 0.821 | +0.089 |
| MAP | 0.688 | 0.784 | +0.096 |
| precision@5 | 0.689 | 0.781 | +0.093 |

This is a real, meaningful offline win. Per the study guide's own framing
("nDCG going up offline means nothing if applications go down online"),
this is treated as a green light to run the A/B, not as proof of anything
by itself.

## 2. Pre-registration (`artifacts/pre_registration.json`) — locked BEFORE the online test ran
- **Hypothesis:** treatment increases `application_rate` (applications /
  impressions, top-10 shown) without hurting `shortlist_rate` or widening
  the fairness parity gap.
- **Primary metric / test:** `application_rate`, fixed-horizon two-proportion
  z-test, α=0.05, power=0.80.
- **MDE:** +8% relative (below this, a win isn't worth the added serving
  cost — practical significance, not just statistical significance).
- **Required sample size:** 46,402 impressions per arm.
- **Decision rule committed in advance:** ship only if the lift is
  significant, positive, meets the MDE, and both guardrails pass — full
  text in the JSON file.
- **`readout.py` enforces this ordering programmatically**: it refuses to
  run unless `pre_registration.json` predates `online_ab_events.csv` on
  disk, so the metric literally cannot be picked after seeing results.

## 3. Online readout (`artifacts/experiment_readout.json`) — the honest part
The 14-day test window produced 9,000 events across 900 postings — **4,580
control impressions and 4,420 treatment impressions**, well short of the
46,402-per-arm requirement computed in the pre-registration. This is
reported as what it is: **an inconclusive test, not a null result** — the
study guide's own vocabulary for exactly this situation.

Reading the numbers anyway, for transparency:
- Primary metric: control 3.86% → treatment 3.64% application rate
  (**-5.75% relative**, p=0.58, **not significant**).
- Secondary (click rate): +4.33% relative, p=0.44, also not significant —
  this is the "wins on clicks but not applications" pattern the
  brainstorming section warns about, visible here even before shortlists
  are considered.
- Guardrails: shortlist rate **passed** (+12.2% relative, well above the
  -5% floor) and fairness parity gap **passed** (treatment gap 0.25pp vs
  control 0.03pp, within the 2pp allowance).
- Practical significance: even setting significance aside, -5.75% is below
  the +8% MDE, so it would not have shipped on effect size alone either.

## 4. Decision (`artifacts/ship_decision.json`)
**DO NOT SHIP — revert to the baseline heuristic ranker.**
Reasoning, applying the pre-registered rule and nothing invented after the
fact: sample size requirement not met, and the primary metric result is
not statistically significant (and numerically negative). Rollback is a
no-op — traffic already defaults to the baseline at the router level (see
§6), so nothing needs to be un-deployed.

This is the specific discipline the study guide is grading: an offline win
(+9.5 points of MAP) did **not** get shipped on offline evidence alone, and
a directionally-negative, underpowered online result did not get
rationalized into a ship.

## 5. Answers to the brainstorming questions (Section 9)
- **"If it wins on clicks but not on shortlists, do you ship?"** — No. The
  guardrail is defined on shortlist rate specifically because clicks are
  the easiest metric to move without moving anything that matters to a
  recruiter; here shortlist rate actually passed, but the primary metric
  didn't, which is why the answer is still no.
- **"Is the lift worth the complexity you are adding forever?"** — This is
  exactly why the decision rule reverts on a neutral/negative result
  instead of shipping a wash: a model that isn't clearly winning still
  costs a permanent serving/monitoring/on-call burden.
- **"What would have made you call this a loss?"** — A significant negative
  primary metric, or a guardrail failure, would have been an unambiguous
  loss. What we actually got — underpowered and slightly negative — is
  logged as inconclusive-leaning-negative, not spun as a loss OR a draw.

## 6. Dependency, failure & edge-case handling (`skew_report.json`, `failure_test_report.json`)
- **Train/serve skew:** `skew_check.py` found real skew — `recency_days`
  mismatched on 98.4% of rows because the serving-time feature path applies
  a caching/timezone offset the training path doesn't (seeded deliberately
  in `features.py` so this check has something real to catch, not a
  no-op). Verdict: **FAIL, must fix before shipping** — this is exactly the
  "silent killer" the study guide names in Section 5.
- **Model unavailable:** `failure_test.py` injected a 30% failure rate into
  the treatment model over 500 simulated requests. Observed fallback-to-baseline
  rate was 32% (consistent within sampling noise) with **zero dropped
  requests** — the router degrades to the baseline heuristic instead of
  erroring.

## 7. Explainability (`artifacts/worked_example.json`)
One real held-out query, ranked by the treatment model, top-5 candidates
each with a plain-English, **directionally-checked** reason (e.g. "ranked
highly because of lower-than-average distance from job location... less of
this trait raises relevance" — not just "high delta," but delta in the
direction that actually helps).

## Pitfalls checklist (Section 12) — self-audit
- [x] Metric chosen after seeing results → **avoided**: enforced by the
  file-timestamp guard in `readout.py`.
- [x] Shipping a model that only won by peeking → **avoided**: single
  fixed-horizon look, no interim checks in the code path.
- [x] Shipping an offline win that never gets validated online →
  **avoided**: this is the entire point of §3 — the offline win was not shipped.
- [x] Fairness audit done once, at the end, as a formality → the parity
  guardrail is computed as a first-class gate in every readout, not a
  post-hoc note.
- [x] No model versioning → **avoided**: `artifacts/model_registry.json`
  hashes and timestamps every trained model version.
