# Task 10 — Growth Integration & Experiment Readout
AI/ML Engineer · Phase 3 · Sprint B — Growth & Experimentation

This is a completed, runnable implementation of Task 10 exactly as scoped by
the study guide: build a live model A/B with a pre-registered hypothesis,
read it out honestly, and make a ship/do-not-ship decision — including the
"discipline to kill your own model if it lost."

**Headline result: the treatment model was tested, and the honest decision
is DO NOT SHIP.** That is not a bug in this submission — it is the exact
discipline Stage 11's scoring rubric is checking for ("A claim without
evidence scores zero"; the study guide explicitly warns against "shipping a
model that only won by peeking"). See `EXPERIMENT_LOG.md` for the full
narrative.

## Why the data is simulated, and why that's stated up front
We do not have access to Altrodav/PlaceMux's real production logs. Stage A
of the pipeline ("confirm every prerequisite is genuinely in hand") requires
being honest about this rather than pretending. `src/data_simulation.py`
generates a realistic stand-in: candidate×job-posting pairs with graded
relevance, a position-biased impression→click→application→shortlist funnel,
and a synthetic candidate "segment" used only as a fairness-audit proxy
(explicitly NOT real demographic data — see the Fairness note below).
Everything downstream — the ranker, the stats test, the decision logic —
runs exactly as it would on real logs; nothing is hard-coded to the
simulation.

## Run it yourself
```bash
pip install -r requirements.txt   # numpy, pandas, scikit-learn, scipy, matplotlib
./run_all.sh
```
Runs Stages A–E in the order the study guide specifies, in ~30 seconds.
Re-running regenerates all data and all `artifacts/*.json` / `artifacts/plots/*.png` from scratch — nothing is pre-baked.

## Design decisions & what was rejected (Stage A.3)
- **LightGBM/XGBoost LambdaMART → scikit-learn GradientBoostingRegressor.**
  This sandbox has no network access; neither package can be installed.
  Pointwise regression on graded relevance is a real, weaker substitute for
  a listwise ranking objective — documented as a limitation in
  `train_ranker.py`, not hidden.
- **Fixed-horizon testing → not sequential/always-valid testing.** Simpler
  to verify by hand and defend to a non-statistician stakeholder; costs
  calendar time when results are unambiguous early. See `pre_registration.json`.
- **Revert-on-neutral → not ship-on-neutral.** The model adds permanent
  serving complexity; a flat result doesn't clear that bar. See
  `pre_registration.json["decision_rule_committed_in_advance"]`.

## Fairness note
`segment_A` / `segment_B` in the simulated data is a **synthetic, made-up
label**, not a real protected characteristic (race, gender, age, etc.). It
exists only so the fairness-parity guardrail in `readout.py` has something
concrete to compute. In a real deployment this would be replaced with
whatever protected-group definitions legal/compliance sign off on, computed
through a proper DPDP-compliant pipeline — that substitution is called out
explicitly rather than glossed over.
